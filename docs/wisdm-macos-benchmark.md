# WISDM Mac 속도·프로세스 메모리 비교

## 결과

2026-11-10 Mac ARM64 CPU에서 실행 방식 6개와 스레드 설정 2개, 총 **12개 조건**을 측정했습니다. 조건마다 독립 프로세스에서 배치 1·워밍업 50회·측정 1,000회를 실행했습니다.

1 MiB는 1,048,576바이트입니다. RSS에는 Python·런타임 import, 모델, 입력·참조 예측 기록, 워밍업과 측정이 포함됩니다. 모델 가중치만의 RAM 사용량이 아닙니다. TFLite 프로세스에서는 TensorFlow를 import하지 않았으며 두 Keras 프로세스에는 TensorFlow 런타임이 포함됩니다.

## 무엇을 알 수 있는가?

- **동적 INT8이 가장 빨랐습니다.** 1스레드 설정에서 FP32 대비 중앙값이 약 31.42% 감소해 약 1.46배 빨랐고, 기본 설정에서도 약 31.01% 감소했습니다.
- **파일이 작다고 항상 빠르지는 않았습니다.** FP16은 파일이 약 44% 작지만 이번 측정에서는 FP32와 지연시간이 비슷했습니다. INT8 입출력 모델은 약 60% 작지만 1스레드 설정 중앙값이 FP32보다 약 54.31% 컸습니다.
- **Keras와 TFLite 사이 차이는 양자화 효과와 구분합니다.** 원본 FP32 모델도 TFLite로 옮기면 호출 경로와 실행 방식이 달라집니다. Keras 직접 호출과 TFLite FP32 사이의 큰 차이를 양자화 덕분이라고 설명하지 않습니다.
- **Keras predict()와 직접 호출도 다릅니다.** predict()에는 데이터 처리·배치 실행 경로 등이 포함됩니다. 측정은 각 호출의 출력이 준비될 때까지이며 순수 연산 커널 시간만 비교한 결과가 아닙니다.
- **양자화로 프로세스 메모리가 크게 줄었다는 근거는 약합니다.** TFLite 모델들의 RSS는 대체로 50MiB 수준으로 비슷했고, 작은 차이를 모델 고유의 RAM 절감으로 단정하지 않습니다.

이 결과는 현재 Mac에서 한 세션에 실행한 관측값입니다. 다른 CPU·Windows·웨어러블에서 같은 속도나 순위가 나온다고 일반화하지 않습니다. INT8 입출력 모델에 float32 NEG 4개가 남아 있다는 [이전 진단](wisdm-quantization.md)을 유지하며, 속도 차이의 원인을 특정 연산 하나로 분해한 실험은 아닙니다.

## 입력과 측정 범위

- 기존 평가 데이터 5,358개 중 seed 42로 1,000개를 중복 없이 골랐습니다. 전처리·모델 해시를 먼저 확인했습니다.
- 12개 조건 모두 같은 구간과 같은 순서를 사용했습니다. 최초 50개로 워밍업한 뒤 선택한 1,000개를 측정했습니다.
- 조건 실행 순서도 seed 42로 섞었으며 실제 순서를 환경 JSON에 남겼습니다. 프로세스는 동시에 여러 개 실행하지 않았습니다.
- 입력 배열 읽기·샘플 선택, 런타임 import, 모델 로드, 인터프리터 생성·텐서 할당은 지연시간 측정에서 제외했습니다.
- Keras 직접 호출은 `model(x, training=False).numpy()`, predict는 `model.predict(x, batch_size=1, verbose=0)`의 반환까지 측정했습니다.
- TFLite는 `set_tensor → invoke → get_tensor`를 포함합니다. INT8 입출력 모델은 입력 양자화·clipping·출력 역양자화도 포함합니다.
- 검증·CSV 쓰기는 개별 호출의 시간 구간 밖에서 수행했습니다. 중앙값·p95는 1,000개 반복의 원시 지연시간으로 계산했고, p95는 NumPy 기본 선형 보간을 사용했습니다.
- 12,000개 출력 모두 유한한 값이며, 선택된 구간의 행동 예측이 앞서 수행한 모델별 전체 평가 기록과 일치했습니다. 이것은 1,000개 구간 점검이며 새로운 전체 정확도 평가로 보고하지 않습니다.

## 스레드·delegate·메모리 의미

1스레드 설정은 TensorFlow intra/inter-op과 관련 수치 연산 환경 변수를 1로 지정하고, LiteRT `num_threads=1`을 요청한 것입니다. **전체 OS 스레드가 하나라는 뜻은 아닙니다.** 보조 파이프라인 등을 포함한 관측 피크 OS 스레드는 Keras predict 25개, 직접 호출 4개였습니다.

기본 설정에서는 이 스레드 환경 변수들을 자식 프로세스에서 제거하고 런타임이 선택하도록 두었습니다. TensorFlow 설정 조회는 intra/inter-op 모두 0(자동)이었으며 관측 피크 스레드는 predict 39개, 직접 호출 18개였습니다. LiteRT는 기본 설정과 1스레드 모두 관측 OS 스레드 1개였고 로그에서 기본 XNNPACK CPU delegate 생성을 확인했습니다. 설정 요청값과 OS 스레드 관측값을 구분합니다.

RSS는 각 독립 프로세스의 macOS `resource.getrusage(RUSAGE_SELF).ru_maxrss`로 기록했습니다. Darwin에서 이 값의 단위는 바이트입니다. 부모 프로세스가 약 10ms마다 관측한 RSS와 OS 스레드 수도 별도 저장했습니다. 이 값은 모델 파일 크기나 모델 실행 전후 RAM 차이가 아닙니다.

## 실행 환경과 한계

- macOS 26.6.2 ARM64, 논리 CPU 8개, Python 3.12.14
- TensorFlow 2.21.0, Keras 3.13.2, LiteRT 2.3.0, NumPy 2.5.4, psutil 7.2.2
- 전원 조회에는 AC Power와 배터리 72%·discharging 상태가 함께 표시돼 원문 상태를 환경 JSON에 기록했습니다.
- 백그라운드 앱과 CPU 주파수·열 상태는 통제하지 않았습니다. CPU 브랜드·물리 RAM의 sysctl 조회는 권한 제한으로 수집하지 못했습니다.
- 모델마다 1,000회 반복했지만 여러 날짜·여러 세션에서 독립 반복한 결과는 아닙니다. 아주 작은 시간·메모리 차이에 우열 의미를 부여하지 않습니다.
