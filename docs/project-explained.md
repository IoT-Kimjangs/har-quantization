# 우리 프로젝트 쉽게 이해하기

우리 프로젝트의 질문은 **“사람의 행동을 알아맞히는 모델을 작게 만들면, 실제로도 빨라질까?”**입니다. 기존 논문을 읽고 공개 코드를 실행한 뒤, Mac과 Windows에서 직접 측정해 확인합니다.

## 사람의 행동을 어떻게 알아맞힐까

스마트폰이나 몸에 착용한 센서는 움직임을 숫자로 기록합니다. 걷기와 뛰기는 센서 값의 변화가 다릅니다. 행동 인식 모델은 이 숫자 패턴을 보고 어떤 행동인지 예측합니다. 이를 HAR, 즉 Human Activity Recognition이라고 부릅니다.

우리 실험은 이미 수집된 WISDM·PAMAP2 데이터를 사용합니다. 팀원이 새로 센서를 달고 데이터를 모으는 작업은 현재 계획에 포함되지 않습니다. 실제 스마트워치에 앱을 설치하는 단계도 현재 실험 범위에 포함되지 않습니다.

## 모델을 왜 작게 만들까

센서 기기에는 저장 공간·메모리·배터리의 제약이 있습니다. 모델을 작게 만들면 기기에 올리기 쉬워질 수 있습니다. 우리가 살펴볼 방법은 모델이 사용하는 숫자의 정밀도를 낮추는 **양자화**입니다.

사진의 화질을 조절해 용량을 줄이는 것과 비슷하게 생각하면 됩니다. 다만 숫자를 단순히 반올림하는 것과 실제 양자화 과정은 다릅니다. 모델 크기와 정확도, 실행 속도가 얼마나 변하는지는 각각 확인해야 합니다.

| 이름 | 쉽게 말하면 |
| --- | --- |
| FP32 | 32비트 실수로 표현한 기준 정밀도 |
| FP16 | 더 적은 비트로 실수를 표현하는 방식 |
| INT8 동적 | 가중치를 8비트로 저장하고 실행 중 연산에 맞게 처리하는 방식 |
| INT8 전체 정수 | 가중치와 중간 계산값을 정수로 표현하도록 변환하는 방식 |

TFLite FP32는 양자화하지 않은 비교 기준입니다. FP16·INT8로 바꿨다고 파일 크기가 정확히 절반·4분의 1이 되거나 속도가 반드시 좋아지는 것은 아닙니다.

## 작아지면 왜 꼭 빨라지지는 않을까

파일 크기는 저장 공간이고, 추론 속도는 입력을 받아 결과를 계산하는 시간입니다. 서로 관련이 있지만 같은 지표는 아닙니다. 숫자 형식을 바꾸는 비용, 사용하는 실행 프로그램, 기기가 지원하는 연산에 따라 작은 모델도 느릴 수 있습니다.

택배 짐의 부피를 줄였어도 포장을 다시 풀고 정리하는 일이 늘어나면 전체 작업 시간이 줄지 않을 수 있는 것과 비슷합니다. 그래서 우리는 모델 크기만 보고 효율이 좋아졌다고 판단하지 않고 시간을 직접 잽니다.

## 기존 논문에서 무엇을 확인할까

선정한 구현체 논문은 HAR용 Transformer 모델과 TFLite 변형을 비교합니다. Transformer는 입력의 여러 부분 사이 관계를 살펴보는 모델이고, 여기서 패치는 긴 센서 기록을 나눈 작은 조각을 뜻합니다.

분석에서 특히 확인할 부분은 **속도 변화가 무엇 때문에 생겼는지**입니다. 원본 모델을 Keras로 실행한 결과와 변환된 모델을 TFLite로 실행한 결과를 곧바로 비교하면, 실행 프로그램을 바꾼 효과와 숫자 정밀도를 바꾼 효과가 함께 들어갑니다.

그래서 아래 순서로 나누어 비교합니다.

| 비교 | 확인하려는 것 |
| --- | --- |
| Keras predict() → Keras model(x) 직접 호출 | 같은 모델도 호출 방법 때문에 시간이 달라지는가 |
| Keras 직접 호출 → TFLite FP32 | 양자화 없이 실행 방식·변환을 바꿨을 때의 차이는 얼마인가 |
| TFLite FP32 → FP16·INT8 | 같은 런타임 안에서 양자화했을 때의 차이는 얼마인가 |

양자화하면 빨라질 것이라는 결론을 먼저 정하지 않습니다. 실제 결과가 같거나 다를 때 모두 실행 조건과 함께 설명합니다.

## 우리가 직접 할 일

1. **논문 읽기:** 서베이 논문으로 분야의 흐름을 파악하고, 구현체 논문의 문제·방법·결과·한계를 정리합니다.
2. **재현하기:** 공개 모델과 코드, 데이터셋을 준비하고 논문과 비슷한 결과가 나오는지 확인합니다.
3. **조건을 맞춰 측정하기:** 같은 입력·반복 횟수·스레드 조건으로 크기·속도·메모리·정확도를 기록합니다.
4. **비교하고 설명하기:** 런타임과 양자화 효과를 나누고 두 플랫폼에서 방식별 순위가 유지되는지 봅니다.
5. **공유하기:** 실행 방법과 결과를 GitHub에 남기고 발표자료·보고서로 정리합니다.

제공된 계획 문서에 적힌 사전 측정값은 참고 자료입니다. 이 저장소에서 새로 실행한 결과는 실행 환경과 원시 기록을 갖춘 별도 결과로 남깁니다.

## Mac과 Windows에서는 무엇을 측정할까

| 항목 | 계획 |
| --- | --- |
| 데이터 | WISDM, PAMAP2 |
| 실행 방식 | Keras predict(), Keras 직접 호출, TFLite FP32·FP16·INT8 동적·INT8 전체 정수 |
| 플랫폼 담당 | 서진정은 Mac ARM, 장은성은 Windows x86 |
| 스레드 조건 | 1스레드, 런타임 기본 설정 |
| 전체 조합 | 데이터 2종 × 실행 방식 6종 × 플랫폼 2종 × 스레드 조건 2종 = 48개 |

Keras는 같은 원본 모델을 두 가지 방식으로 호출합니다. 따라서 “서로 다른 모델 6개”보다는 “실행 방식 6개”라고 이해하면 됩니다. 각 플랫폼에서 24개 조합을 맡습니다.

본 측정은 배치 1, 워밍업 50회, 측정 1,000회를 기준으로 합니다. 처음 몇 번 실행은 준비 과정의 영향을 받을 수 있으므로 워밍업은 실제 측정에서 제외합니다.

## 결과표에서 볼 숫자

| 지표 | 뜻 | 확인할 점 |
| --- | --- | --- |
| 모델 파일 크기 | 저장된 모델이 차지하는 공간 | 무엇을 기준으로 압축률을 계산했는지 |
| 지연시간 중앙값 | 반복 실행 시간을 정렬했을 때 가운데 값 | 보통 어느 정도 시간이 걸리는지 |
| p95 지연시간 | 측정값의 약 95%가 이 값 이하인 시간 | 느리게 실행되는 경우가 어느 정도인지 |
| 프로세스 피크 메모리 | 실행 중 프로세스가 사용한 메모리의 최대치 | Python·런타임까지 포함한다는 점 |
| 정확도 | 전체 예측 중 맞힌 비율 | 실제 테스트 데이터로 평가했는지 |
| Macro-F1 | 행동별 F1 점수를 같은 비중으로 평균한 값 | 특정 행동에서만 성능이 낮지 않은지 |

무작위 숫자를 입력해 재는 시간은 실행 속도 점검에는 쓸 수 있지만, 사람의 행동을 얼마나 잘 맞히는지를 보여 주는 정확도 결과는 아닙니다.

## 각자 맡는 일

- **김가은:** 논문 분석, 문제와 한계 정리, 발표·보고서 구성과 제출 총괄.
- **서진정:** Mac 환경, 모델 재현·측정, 양자화 방식 분석, GitHub 실행 문서.
- **장은성:** Windows 환경, 모델 재현·측정, 공통 측정 스크립트, 결과 표·그래프.

장은성이 준비하는 측정 스크립트는 서진정도 Mac에서 검증합니다. 세 명 모두 논문과 결과를 함께 이해하고, 작업은 브랜치와 PR로 공유합니다.

## 최종적으로 무엇을 남길까

논문의 핵심과 한계 분석, 재현 결과, 48개 조합의 결과 또는 실행 불가 사유, 비교 표·그래프, 실행 방법, 발표자료와 보고서를 남깁니다.

이 실험으로 특정 HAR 모델에서 양자화 방식의 차이를 설명할 수 있습니다. 노트북 두 대의 결과만으로 모든 ARM·x86 기기의 우열이나 실제 스마트워치 성능까지 결론 내리지는 않습니다.
