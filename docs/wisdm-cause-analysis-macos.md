# WISDM 원인 분석 1차 결과 (Mac)

INT8 입출력 모델이 FP32보다 느린 이유를 좁히기 위한 1차 실험입니다. [확장 실험 계획](extension-plan.md)의 실험 1(입출력 변환 비용 분리)과 실험 3(기본 CPU 가속 켜고 끄기)을 WISDM·Mac에서 먼저 실행했습니다. 원인이 가장 크게 나타난 Windows 실행 전의 소규모 검증이므로, 아래 해석은 Mac 범위에 한정합니다.

## 무엇을 했나

| 항목 | 내용 |
| --- | --- |
| 모델 | 기존 TFLite FP32·FP16·동적 INT8·INT8 입출력 + 새로 만든 **INT8 실수 입출력** |
| 새 모델 | INT8 입출력과 같은 변환 설정·같은 보정 구간 300개로 변환하되, 입력과 출력만 float32로 둠 ([변환 스크립트](../scripts/quantize_wisdm_int8_float_io.py)) |
| 시간 나누기 | 호출마다 ① 입력 정수 변환 ② `set_tensor`+`invoke` ③ 출력 읽기·실수 복원을 따로 기록 |
| 가속 | 기본 설정(XNNPACK 사용)과 `BUILTIN_WITHOUT_DEFAULT_DELEGATES`(기본 가속 끔) |
| 조건 | 5개 모델 × 가속 2 × 스레드 2(1·기본) × **반복 3회** = 60회, 회마다 새 프로세스 |
| 측정 규약 | 기존과 같음: 배치 1, 워밍업 50회, 1,000회 호출, 모델 로드 시간 제외 |

변환 재현성 확인: 같은 설정으로 INT8 입출력 모델을 다시 변환하면 기록된 파일과 **바이트 단위로 같았습니다**. 새 INT8 실수 입출력 모델은 평가 구간 5,358개 전부에서 INT8 입출력 모델과 예측이 100% 같았습니다(정확도 96.715%, 5,182개). 두 모델의 차이는 입출력 형식뿐이라고 볼 수 있습니다.

결과: [반복별 기록](../results/2026-11-28-macos-wisdm-cause/runs.csv) · [조건별 요약](../results/2026-11-28-macos-wisdm-cause/summary.csv) · [새 모델 평가](../results/2026-11-28-macos-wisdm-int8-float-io/metrics.json)

## 결과

기본 설정, 3회 반복의 중앙값입니다. 반복 간 차이는 모든 조건에서 약 0.6% 이내였고, 기존 48개 조건 측정값(FP32 0.04475 ms, INT8 입출력 0.06929 ms)과도 거의 같았습니다.

### 1. 입출력 변환은 차이의 약 3분의 1

| 모델 | 입력 변환 | 실행 (set+invoke) | 출력 복원 | 합계 (ms) | FP32 대비 |
| --- | ---: | ---: | ---: | ---: | ---: |
| TFLite FP32 | 0.00004 | 0.04417 | 0.00058 | 0.04479 | 1.00배 |
| INT8 입출력 | 0.00529 | 0.06088 | 0.00292 | 0.06913 | 1.54배 |
| INT8 실수 입출력 | 0.00004 | 0.06088 | 0.00058 | 0.06146 | 1.37배 |

- FP32와 INT8 입출력의 차이 0.0243 ms 중 입력 변환과 출력 복원이 약 0.0076 ms로 **약 3분의 1**입니다.
- 나머지 약 3분의 2(0.0167 ms)는 모델 실행 자체에서 생깁니다. 입출력을 실수로 둔 모델도 FP32보다 1.37배 느렸습니다.
- 따라서 Mac에서는 **입출력 변환만으로는 느려짐을 설명할 수 없습니다.**

### 2. 기본 가속(XNNPACK)과의 관계

| 모델 | 가속 켬 (ms) | 가속 끔 (ms) | 가속 효과 | 가속 구간 수 |
| --- | ---: | ---: | ---: | ---: |
| TFLite FP32 | 0.04479 | 0.08450 | 1.89배 | 1 |
| FP16 | 0.04492 | 0.08533 | 1.90배 | 2 |
| 동적 INT8 | 0.03083 | 0.06679 | 2.17배 | 1 |
| INT8 입출력 | 0.06913 | 0.13283 | 1.92배 | 17 |
| INT8 실수 입출력 | 0.06146 | 0.12488 | 2.03배 | 19 |

- FP32·동적 INT8은 그래프 전체가 가속 구간 1개로 묶였지만, INT8 두 모델은 **17~19개 구간으로 잘게 나뉘었습니다.** 가속되지 않는 연산이 중간중간 끼어 있다는 뜻입니다.
- 그런데 가속을 끄면 모든 모델이 비슷하게(약 1.9~2.2배) 느려지고, INT8 입출력은 가속을 끈 상태에서도 FP32보다 1.57배 느렸습니다.
- 즉 Mac에서는 "INT8만 가속을 못 받아서 느리다"고 보기 어렵습니다. **INT8 경로의 연산 자체가 이 모델에서 더 오래 걸리는 쪽**에 가깝습니다. 구간이 잘게 나뉜 것이 얼마나 영향을 주는지는 연산별 시간을 재야 확인할 수 있습니다.

### 3. 스레드 설정

Mac에서는 스레드 1과 기본 설정의 차이가 모든 모델에서 0.5% 이내였습니다. 기존 결과와 같습니다. FP16이 스레드 설정에 따라 뒤집힌 현상은 Windows에서만 나타났으므로 Windows 실행에서 확인해야 합니다.

### 참고: 가속을 끈 INT8 모델의 예측

가속을 끈 INT8 두 모델은 1,000개 중 3개(반복마다 같은 3개)에서 기존 평가와 예측이 달랐습니다. 가속기와 기본 정수 연산의 반올림 차이로 보이며, 가속을 끈 조건은 원인 확인용이라 정확도 결과로 쓰지 않습니다. 가속을 켠 조건은 모든 모델에서 기존 평가와 100% 같았습니다.

## 지금까지의 해석 (Mac)

- INT8 입출력이 느린 이유 중 **약 3분의 1은 입출력 변환**, **약 3분의 2는 모델 안쪽 INT8 실행**입니다.
- 모델 안쪽에는 `QUANTIZE` 5개·`DEQUANTIZE` 5개와 LayerNormalization의 `NEG` 4개가 남아 있고, 가속 구간이 17~19개로 나뉩니다. 이 연산들이 실제로 시간을 차지하는지는 아직 확인하지 않았습니다.
- Mac의 차이(1.54배)는 Windows(3.94배)보다 작습니다. 원인의 비중은 Windows에서 달라질 수 있습니다.

## 다음 단계

1. **Windows 실행 (장은성):** 같은 두 스크립트를 Windows 모델·기록으로 실행합니다. 3.94배 차이와 FP16 스레드 역전이 위 두 실험으로 어떻게 나뉘는지가 핵심입니다.
2. **연산별 시간:** INT8 모델 안쪽에서 시간이 어디에 쓰이는지 TFLite 연산별 프로파일링으로 확인합니다. 두 OS에서 도구가 동작하는지 먼저 확인합니다.

### Windows 실행 명령

Windows 변환·양자화 결과 폴더를 `--quant-result`로 지정합니다. 모델 해시가 그 기록과 맞아야 실행됩니다.

```powershell
.venv\Scripts\python.exe scripts/quantize_wisdm_int8_float_io.py --output results/<날짜>-windows-wisdm-int8-float-io --quant-result results/2026-11-10-windows-wisdm-quantization
.venv\Scripts\python.exe scripts/benchmark_wisdm_cause.py --output results/<날짜>-windows-wisdm-cause --quant-result results/2026-11-10-windows-wisdm-quantization --float-io-result results/<날짜>-windows-wisdm-int8-float-io
```

Windows에서는 아직 실행해 보지 않았습니다. 첫 실행에서 오류가 나면 해당 `.log`와 함께 알려주세요.

## 실행 환경

Mac ARM64 (Apple M1 Pro), Python 3.12.14, `ai-edge-litert` 2.3.0, TensorFlow 2.21.0. 배경 앱과 CPU 주파수는 통제하지 않았습니다. 가속을 끈 조건은 원인 확인용 비교이며 권장 실행 설정이 아닙니다.
