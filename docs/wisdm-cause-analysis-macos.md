# WISDM 원인 분석 1차 결과 (Mac)

INT8 입출력 모델이 FP32보다 느린 이유를 좁히기 위한 1차 실험입니다. [확장 실험 계획](extension-plan.md)의 입출력 변환 비용 분리, 기본 CPU 가속 켜고 끄기, 연산별 시간 측정을 WISDM·Mac에서 먼저 실행했습니다. 원인이 가장 크게 나타난 Windows 실행 전의 소규모 검증이므로, 아래 해석은 Mac 범위에 한정합니다.

## 무엇을 했나

| 항목 | 내용 |
| --- | --- |
| 모델 | 기존 TFLite FP32·FP16·동적 INT8·INT8 입출력 + 새로 만든 **INT8 실수 입출력** |
| 새 모델 | INT8 입출력과 같은 변환 설정·같은 보정 구간 300개로 변환하되, 입력과 출력만 float32로 둠 ([변환 스크립트](../scripts/quantize_wisdm_int8_float_io.py)) |
| 시간 나누기 | 호출마다 ① 입력 정수 변환 ② `set_tensor`+`invoke` ③ 출력 읽기·실수 복원을 따로 기록 |
| 가속 | 기본 설정(XNNPACK 사용)과 `BUILTIN_WITHOUT_DEFAULT_DELEGATES`(기본 가속 끔) |
| 조건 | 5개 모델 × 가속 2 × 스레드 2(1·기본) × **반복 3회** = 60회, 회마다 새 프로세스 |
| 측정 규약 | 기존과 같음: 배치 1, 워밍업 50회, 1,000회 호출, 모델 로드 시간 제외 |

변환 재현성 확인: 같은 설정으로 INT8 입출력 모델을 다시 변환하면 기록된 파일과 **바이트 단위로 같았습니다**. 새 INT8 실수 입출력 모델은 평가 구간 5,358개 전부에서 INT8 입출력 모델과 예측이 100% 같았습니다(정확도 96.715%, 5,182개). 두 모델의 차이는 입출력 형식뿐이라고 볼 수 있습니다.

결과: [반복별 기록](../results/2026-11-28-macos-wisdm-cause/runs.csv) · [조건별 요약](../results/2026-11-28-macos-wisdm-cause/summary.csv) · [새 모델 평가](../results/2026-11-28-macos-wisdm-int8-float-io/metrics.json)

## 결과

기본 설정, 3회 반복의 중앙값입니다. 반복 간 차이는 모든 조건에서 약 0.6% 이내였고, 기존 48개 조건 측정값(FP32 0.04475 ms, INT8 입출력 0.06929 ms)과도 거의 같았습니다.

### 1. 입출력 변환은 차이의 약 3분의 1 (Python 측정 기준)

| 모델 | 입력 변환 | 실행 (set+invoke) | 출력 복원 | 합계 (ms) | FP32 대비 |
| --- | ---: | ---: | ---: | ---: | ---: |
| TFLite FP32 | 0.00004 | 0.04417 | 0.00058 | 0.04479 | 1.00배 |
| INT8 입출력 | 0.00529 | 0.06088 | 0.00292 | 0.06913 | 1.54배 |
| INT8 실수 입출력 | 0.00004 | 0.06088 | 0.00058 | 0.06146 | 1.37배 |

- FP32와 INT8 입출력의 차이 0.0243 ms 중 입력 변환과 출력 복원이 약 0.0076 ms로 **약 3분의 1**입니다.
- 나머지 약 3분의 2(0.0167 ms)는 모델 실행 자체에서 생깁니다. 입출력을 실수로 둔 모델도 FP32보다 1.37배 느렸습니다.
- 따라서 Mac에서는 **입출력 변환만으로는 느려짐을 설명할 수 없습니다.** 이 변환 비용의 성격은 4번에서 다시 봅니다.

### 2. 기본 가속(XNNPACK)과의 관계

| 모델 | 가속 켬 (ms) | 가속 끔 (ms) | 가속 효과 | 가속 구간 수 |
| --- | ---: | ---: | ---: | ---: |
| TFLite FP32 | 0.04479 | 0.08450 | 1.89배 | 1 |
| FP16 | 0.04492 | 0.08533 | 1.90배 | 2 |
| 동적 INT8 | 0.03083 | 0.06679 | 2.17배 | 1 |
| INT8 입출력 | 0.06913 | 0.13283 | 1.92배 | 17 |
| INT8 실수 입출력 | 0.06146 | 0.12488 | 2.03배 | 19 |

- FP32·동적 INT8은 그래프 전체가 가속 구간 1개로 묶였지만, INT8 두 모델은 **17~19개 구간으로 잘게 나뉘었습니다.** 가속되지 않는 연산이 중간중간 끼어 있다는 뜻입니다.
- 그런데 가속을 끄면 모든 모델이 비슷하게(약 1.9~2.2배) 느려지고, INT8 입출력은 가속을 끈 상태에서도 FP32보다 1.57배 느렸습니다.
- 즉 Mac에서는 "INT8만 가속을 못 받아서 느리다"고 보기 어렵습니다. **INT8 경로의 연산 자체가 이 모델에서 더 오래 걸리는 쪽**에 가깝습니다. 구간이 잘게 나뉜 것이 얼마나 영향을 주는지는 연산별 시간을 재야 확인할 수 있습니다.

### 3. 스레드 설정

Mac에서는 스레드 1과 기본 설정의 차이가 모든 모델에서 0.5% 이내였습니다. 기존 결과와 같습니다. FP16이 스레드 설정에 따라 뒤집힌 현상은 Windows에서만 나타났으므로 Windows 실행에서 확인해야 합니다.

### 참고: 가속을 끈 INT8 모델의 예측

가속을 끈 INT8 두 모델은 1,000개 중 3개(반복마다 같은 3개)에서 기존 평가와 예측이 달랐습니다. 가속기와 기본 정수 연산의 반올림 차이로 보이며, 가속을 끈 조건은 원인 확인용이라 정확도 결과로 쓰지 않습니다. 가속을 켠 조건은 모든 모델에서 기존 평가와 100% 같았습니다.

### 4. 연산별 시간: LayerNormalization의 INT8 연산이 가속 밖에서 오래 걸림

TFLite 공식 측정 도구(`benchmark_model --enable_op_profiling`)는 Mac·Windows용 배포판이 없어, 같은 Mac에서 Podman 리눅스 VM(4 vCPU)을 띄워 리눅스 ARM64용 공식 nightly 도구로 측정했습니다. 운영체제가 다르므로 절대 시간보다 **어느 연산이 시간을 쓰는지**를 봅니다. 스레드 1, 워밍업 50회, 1,000회 실행, 도구 기본 무작위 입력입니다. ([도구 출력과 실행 정보](../results/2026-11-28-linux-arm64-vm-wisdm-op-profile/run-info.json))

| 모델 | 가속 켬 (µs) | 가속 끔 (µs) |
| --- | ---: | ---: |
| TFLite FP32 | 20.9 | 87.8 |
| FP16 | 20.7 | 90.4 |
| 동적 INT8 | 17.7 | 88.2 |
| INT8 입출력 | 34.0 | 130.3 |
| INT8 실수 입출력 | 34.7 | 132.1 |

가속을 켠 INT8 입출력 모델의 연산별 시간(도구가 ms 소수 셋째 자리까지만 표시):

| 연산 | 개수 | 시간 (ms) | 비율 | 가속 여부 |
| --- | ---: | ---: | ---: | --- |
| `SQUARED_DIFFERENCE` (LayerNormalization 분산 계산) | 4 | 0.016 | 72.7% | 가속 밖, 기본 INT8 커널 |
| `BATCH_MATMUL` (어텐션) | 4 | 0.004 | 18.2% | 가속 밖 |
| `SOFTMAX` | 3 | 0.002 | 9.1% | 가속 밖 |
| 나머지(Fully Connected 등, XNNPACK) | — | 0.000 표시 | — | 가속 안 |

- FP32 모델은 모든 연산이 가속 안에서 실행됐습니다. INT8 두 모델은 **LayerNormalization의 `SQUARED_DIFFERENCE` 4개, 어텐션의 `BATCH_MATMUL` 4개, `SOFTMAX` 3개가 가속을 받지 못하고** 기본 INT8 커널로 실행됐고, 이 연산들이 측정된 연산 시간의 대부분을 차지했습니다. 가속 구간이 17~19개로 쪼개진 이유도 이 연산들이 중간에 끼기 때문입니다.
- 가속을 끈 FP32에서 `SQUARED_DIFFERENCE` 4개는 0.004 ms였지만, INT8에서는 가속을 켜도 0.016 ms였습니다. 같은 연산이 INT8 기본 커널에서 약 4배 오래 걸립니다.
- 도구 안에서는 INT8 입출력(입력을 정수로 바로 넣음)과 INT8 실수 입출력(모델 안에서 변환)의 차이가 0.7 µs뿐이었습니다. 1번 표에서 입출력 변환이 약 7.6 µs였던 것은 **Python(NumPy)으로 변환한 비용**이며, 변환 자체가 본질적으로 비싼 것은 아닙니다.

### 5. PAMAP2에서도 같은 연산이 가속 밖에 있음

같은 방법으로 PAMAP2 모델 4개를 측정했습니다. ([도구 출력](../results/2026-11-28-linux-arm64-vm-pamap2-op-profile/run-info.json))

| 모델 | 가속 켬 (µs) | 가속 끔 (µs) |
| --- | ---: | ---: |
| TFLite FP32 | 221.7 | 371.8 |
| FP16 | 221.8 | 371.5 |
| 동적 INT8 | 102.4 | 272.9 |
| INT8 입출력 | 161.5 | 498.3 |

- 가속을 켠 INT8 입출력 모델에서 LayerNormalization의 `SQUARED_DIFFERENCE` 6개가 0.078 ms로 연산 시간의 약 54%를 차지했습니다. 같은 연산이 FP32에서는 가속을 꺼도 0.018 ms라, INT8 기본 커널에서 약 4배 오래 걸리는 점이 WISDM과 같습니다. `SOFTMAX`·`BATCH_MATMUL`도 가속 밖에 있었습니다.
- 다만 PAMAP2는 입력(200×19)과 Fully Connected 계산이 커서, FP32에서는 Fully Connected가 시간의 약 81%를 차지합니다. INT8에서 이 부분이 크게 줄어(0.174 → 0.027 ms) 느린 LayerNormalization을 상쇄하므로, 이 도구에서는 INT8 입출력이 FP32보다 빨랐습니다.
- 즉 **INT8 입출력이 빨라질지 느려질지는 "INT8로 크게 줄어드는 행렬 계산"과 "INT8에서 느려지는 LayerNormalization 계산"의 비중에 달려 있습니다.** 계산량이 작은 WISDM 모델에서는 느려지는 쪽이 이겼습니다.
- Python으로 잰 기존 Mac 결과(PAMAP2 INT8 입출력 1.03배)와 방향이 다른 것은 Python 입력 변환 비용(입력이 WISDM의 약 16배 크기)과 운영체제 차이 때문일 수 있으며, 아직 나눠 확인하지 않았습니다.

## 지금까지의 해석 (Mac)

- INT8 입출력이 FP32보다 느린 주된 이유는 **Transformer의 LayerNormalization·어텐션 일부 연산이 (WISDM·PAMAP2 모두) INT8에서 CPU 가속(XNNPACK)을 받지 못하고 느린 기본 커널로 실행되기 때문**으로 보입니다. 특히 LayerNormalization의 `SQUARED_DIFFERENCE`가 가장 큽니다.
- Python 측정에서 보인 입출력 변환 비용(차이의 약 3분의 1)은 Python으로 변환한 구현 비용입니다. 실제 기기에서 입력을 정수로 바로 받으면 이 부분은 거의 없어질 수 있습니다.
- 가속을 끄면 모든 모델이 비슷하게 느려지므로 "가속을 못 받는다"만으로는 부족하고, **INT8 기본 커널이 이 연산들에서 FP32보다 느린 것**이 함께 작용합니다.
- 한계: 연산별 시간은 Mac이 아닌 리눅스 VM 결과이고 도구 표시 단위가 1 µs라 작은 연산은 0으로 보입니다. Mac 차이(1.54배)는 Windows(3.94배)보다 작으므로 Windows에서 같은 연산이 더 느린지 확인해야 합니다.

## 다음 단계

1. **Windows 실행 (장은성):** 같은 두 스크립트를 Windows 모델·기록으로 실행합니다. 3.94배 차이와 FP16 스레드 역전이 입출력 변환·가속 켜고 끄기로 어떻게 나뉘는지가 핵심입니다.
2. **Windows 연산별 시간:** 공식 Windows 도구가 없으므로, Windows에서 WSL2(리눅스 x86-64)로 `linux_x86-64_benchmark_model`을 실행하는 방법을 검토합니다.
3. **PAMAP2 Python 측정:** 연산별 시간에서는 PAMAP2 INT8 입출력이 FP32보다 빨랐으므로, 기존 Python 측정(1.03배)과의 차이가 입력 변환 비용 때문인지 `benchmark_wisdm_cause.py`와 같은 방식으로 나눠 확인합니다.

### Windows 실행 명령

Windows 변환·양자화 결과 폴더를 `--quant-result`로 지정합니다. 모델 해시가 그 기록과 맞아야 실행됩니다.

```powershell
.venv\Scripts\python.exe scripts/quantize_wisdm_int8_float_io.py --output results/<날짜>-windows-wisdm-int8-float-io --quant-result results/2026-11-10-windows-wisdm-quantization
.venv\Scripts\python.exe scripts/benchmark_wisdm_cause.py --output results/<날짜>-windows-wisdm-cause --quant-result results/2026-11-10-windows-wisdm-quantization --float-io-result results/<날짜>-windows-wisdm-int8-float-io
```

Windows에서는 아직 실행해 보지 않았습니다. 첫 실행에서 오류가 나면 해당 `.log`와 함께 알려주세요.

## 실행 환경

Mac ARM64 (Apple M1 Pro), Python 3.12.14, `ai-edge-litert` 2.3.0, TensorFlow 2.21.0. 배경 앱과 CPU 주파수는 통제하지 않았습니다. 가속을 끈 조건은 원인 확인용 비교이며 권장 실행 설정이 아닙니다.
