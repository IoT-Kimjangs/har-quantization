# TinyML 행동 인식 서베이 정리

작은 기기에서 사람의 행동을 인식하려면 모델만이 아니라 데이터 처리·실행 프로그램·하드웨어·측정 방법까지 함께 봐야 한다는 논문입니다. 우리 과제에서는 연구 배경과 평가 기준을 정리하는 데 사용합니다.

원문: *A Review of TinyML for Human Activity Recognition on Edge Devices*, Machine Learning and Knowledge Extraction, 2026, 8, 271. [DOI 및 원문](https://doi.org/10.3390/make8090271). 아래 페이지는 PDF에 인쇄된 쪽수 기준입니다.

## 어떤 논문인가

새 모델 하나를 제안해 성능을 검증하는 연구가 아니라 기존 TinyML HAR 연구를 모아 분류·비교하는 서베이입니다. 검색 범위는 2020년 1월부터 2026년 5월까지이며, 저자들은 검색 기록 536개에서 중복 제거와 선별을 거쳐 최종 47개 연구를 선정했다고 보고합니다(7~9쪽).

서로 다른 연구의 성능을 같은 환경에서 새로 측정한 통합 벤치마크는 아닙니다. 기기·데이터·측정 범위가 다른 기존 결과를 모았으므로 숫자만으로 모델 순위를 단정하기 어렵습니다.

## HAR와 TinyML

HAR는 센서 기록으로 걷기·뛰기·앉기 같은 행동을 구분하는 기술입니다. TinyML은 메모리·계산 능력·전력이 제한된 작은 기기에서 머신러닝을 실행하도록 만드는 분야입니다.

예를 들어 손목 센서가 움직임을 숫자로 기록하면 모델이 그 패턴으로 행동을 예측합니다. 기기에서 직접 처리하면 통신 의존도를 낮출 수 있지만, 정확도가 높아도 너무 크거나 느리고 에너지를 많이 쓰면 실제 사용이 어렵습니다.

## 행동 인식 과정을 어떻게 나누나

4장과 16쪽 표 4는 센서 입력부터 실제 실행까지 다음 요소로 분류합니다.

| 요소 | 확인할 질문 |
| --- | --- |
| 센서와 배치 | 어떤 센서를 어디에 달고 몇 Hz로 기록했나? |
| 전처리와 구간 분할 | 잡음·누락값을 어떻게 처리하고 몇 시점씩 잘랐나? |
| 특징 표현과 센서 융합 | 원시 신호를 쓰는가, 특징을 추출하는가, 여러 센서를 어디서 합치는가? |
| 모델과 학습 | 어떤 모델을 쓰며 새로운 사람·환경에 적응하는가? |
| 경량화와 최적화 | 양자화·가지치기·증류 또는 연산 최적화를 적용했나? |
| 실행 환경 | 어떤 런타임과 하드웨어에서 동작하나? |
| 성능 보고 | 정확도·메모리·지연시간·에너지를 어떤 조건으로 측정했나? |

같은 모델이라도 센서 위치, 윈도우 길이, 데이터 분할, 실행 환경이 바뀌면 결과가 달라질 수 있습니다. 모델 구조만 기록해서는 충분하지 않습니다.

## 경량화 기법 비교

4.5.2절과 표 6(19~21쪽)이 우리 주제와 직접 연결됩니다.

| 방법 | 쉬운 설명 | 실제 적용에서 확인할 점 |
| --- | --- | --- |
| 양자화 | 가중치·활성값을 더 적은 비트로 표현 | 정확도 변화, 보정 데이터, 정수 연산 지원 |
| 가지치기 | 불필요한 연결·채널 등을 제거 | 줄어든 연결을 실제 계산 절감으로 활용하는지 |
| 지식 증류 | 큰 모델의 예측을 작은 모델이 배우도록 학습 | 작은 모델의 구조와 추가 학습 비용 |
| NAS | 자원 제약에 맞는 구조를 자동으로 탐색 | 탐색 목표가 실제 기기의 비용을 반영하는지 |

논문은 양자화가 여러 연구에서 유용했다고 정리하지만 무조건적인 속도 향상을 보장하지는 않습니다. 구조적 가지치기와 달리 비구조적 가지치기는 연결을 많이 지워도 희소 연산 지원이 없으면 빨라지지 않을 수 있습니다. 지식 증류 역시 작은 모델의 구조가 비효율적이면 지연시간 개선이 제한됩니다.

## 함께 봐야 할 평가 지표

5.1절과 표 8(23쪽)은 인식 품질과 실행 비용을 함께 다룹니다.

| 지표 | 뜻 | 구분할 내용 |
| --- | --- | --- |
| 정확도·F1 | 행동을 얼마나 잘 맞히는지 | 불균형 데이터에서는 행동별 성능과 Macro-F1 확인 |
| Flash·모델 크기 | 저장 공간에서 차지하는 크기 | 모델 파일 크기는 가중치 저장 비용의 대리 지표일 수 있음 |
| 피크 RAM | 추론 중 동적 메모리 최대 사용량 | 입력 버퍼·중간 계산값·실행 버퍼도 필요 |
| 지연시간 | 한 윈도우 또는 샘플의 처리 시간 | 모델 계산만인지 전처리·데이터 수집까지 포함하는지 |
| 추론당 에너지 | 한 번 예측할 때 소비한 에너지 | 소비 전력과 구분하고 측정 구간 명시 |

논문은 원 연구에서 보고하지 않았고 가정 없이 계산할 수도 없는 지표는 미보고로 표시합니다. 누락값을 추정해 채우지 않는 원칙도 우리 결과표에 적용합니다.

36쪽에서는 같은 보드 계열에서도 보고된 지연시간이 크게 다를 수 있다고 설명합니다. 모델만 잰 시간과 전처리·전체 스트리밍 시간을 섞으면 공정한 비교가 되지 않기 때문입니다.

## 실제 사용에 남은 문제

6장(36~38쪽)의 주요 쟁점은 다음과 같습니다.

- 다른 사람이나 다른 센서 착용 위치에서 성능이 떨어질 수 있습니다.
- 전체 정확도가 높아도 드문 행동을 놓치는 문제가 가려질 수 있습니다.
- 실험실 데이터는 잡음·누락·센서 드리프트 등 실제 조건을 충분히 반영하지 못할 수 있습니다.
- 윈도우·데이터 분할·기기·런타임·측정 범위가 달라 재현과 비교가 어려울 수 있습니다.

7장에서는 개인화·연합학습·생성형 AI·센서 융합·뉴로모픽 하드웨어 등을 향후 방향으로 논의합니다. 이번 과제에서 이 항목을 모두 구현하는 것은 아닙니다.

## 우리 프로젝트에 적용할 내용

모델 파일 크기를 줄이는 것과 실제 실행이 빨라지는 것은 따로 확인합니다. 파일 크기, 지연시간 중앙값·p95, 프로세스 메모리, 정확도·Macro-F1을 기록하고 OS·CPU·패키지·스레드·런타임 조건을 남깁니다.

마이크로컨트롤러의 피크 RAM과 노트북 Python 프로세스의 피크 RSS는 측정 대상과 범위가 다릅니다. 서로 같은 지표처럼 비교하지 않습니다. 또한 우리 계획에는 에너지 실측이 포함되지 않았으므로 크기·속도 결과만으로 배터리 절감량을 주장하지 않습니다.

이 서베이는 평가 관점을 제공하며, 우리 Keras/TFLite 비교의 효과를 직접 실험해 증명한 자료는 아닙니다. 구체적인 비교 대상과 수치는 [구현체 논문 정리](quantized-patch-transformer.md), 전체 연결은 [논문 읽기 안내](README.md)에서 확인합니다.
