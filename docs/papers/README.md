# 선정 논문 읽기 안내

우리 과제는 기존 연구를 이해하고, 구현체 논문 하나를 분석·재현한 뒤, 조건을 바꿔 확장 실험하는 프로젝트입니다. 두 논문은 서로 다른 역할을 맡습니다.

| 자료 | 역할 | 과제에서 사용할 내용 |
| --- | --- | --- |
| [TinyML HAR 서베이 정리](tinyml-har-survey.md) | 분야 전체를 보는 안내서 | 경량화의 필요성, 기법 분류, 평가 지표, 공정한 비교 조건 |
| [양자화 패치 Transformer 논문 정리](quantized-patch-transformer.md) | 직접 분석하고 재현할 실험 대상 | 모델 구조, 데이터 처리, 양자화 방식, 원 논문 결과와 한계 |
| 우리 팀의 확장 실험 | 기존 결과를 추가 조건에서 확인 | 호출 방식·런타임·양자화 효과 구분, Mac·Windows 비교 |

## 두 논문이 이어지는 흐름

서베이는 작은 기기의 행동 인식에서 정확도뿐 아니라 크기·속도·메모리·에너지도 중요하다는 배경을 제공합니다. 이 관점으로 구현체 논문의 결과표와 측정 조건을 읽고, 실제 실행으로 확인할 질문을 정합니다.

```text
서베이로 문제와 평가 기준 이해
→ 구현체 논문의 방법·결과·조건 분석
→ 공개 모델·코드로 결과 재현
→ 조건을 맞춘 확장 실험
→ 발표·보고서에 근거와 한계 정리
```

우리 질문은 “작아진 모델이 실제로도 빨라지는가?”입니다. 원본 Keras와 양자화된 TFLite를 한 번에 비교하면 호출 방법·변환·런타임·양자화의 영향이 섞일 수 있으므로 다음 비교를 나눕니다.

| 비교 | 확인할 영향 |
| --- | --- |
| Keras predict() → Keras model(x) 직접 호출 | 같은 모델의 호출 방식 |
| Keras 직접 호출 → TFLite FP32 | 변환·런타임 변경과 실행 경로 |
| TFLite FP32 → FP16·INT8 | 같은 런타임에서 양자화 방식 변경 |

이 비교 설계는 우리 팀의 확장 계획입니다. 서베이가 이 실험을 직접 수행했거나, 구현체 논문이 각 효과를 이미 분리해 증명했다고 적지 않습니다. 실제 차이와 원인은 측정 후 판단합니다.

## 처음 읽는 순서

1. 서베이 정리에서 HAR·TinyML의 뜻과 평가 지표를 읽습니다.
2. 구현체 논문 원문의 8쪽 그림 8로 모델 구조를 봅니다.
3. 10쪽 실험 조건과 11~12쪽 표 4~8을 함께 확인합니다.
4. 15쪽 한계를 읽고 재현할 항목과 추가로 확인할 항목을 구분합니다.
5. 서베이 원문의 19~21쪽, 23쪽, 36쪽, 38쪽으로 돌아가 비교 기준을 점검합니다.

읽으면서 “어떤 문제를 풀었나?”, “무엇과 비교했나?”, “무엇을 직접 측정했나?”를 메모합니다. 모든 수식과 참고문헌부터 읽기보다 입력·출력·비교 대상·실험 조건을 먼저 이해합니다.

## 발표와 보고서에 쓰는 방법

- 연구 배경: 센서 기기에서 경량화가 필요한 이유를 서베이로 설명합니다.
- 문제 분석: 구현체 논문의 모델·양자화 방식·비교 조건과 한계를 정리합니다.
- 재현 결과: 원 논문 수치와 우리 측정값을 구분해 나란히 보고합니다.
- 확장 결과: 호출 방식·런타임·양자화의 영향을 나눠 해석합니다.
- 결론: 노트북 두 대의 결과를 전체 ARM/x86 또는 실제 스마트워치의 성능으로 확대하지 않습니다.

각 정리 문서에는 원문 페이지와 표 번호를 적었습니다. 표의 수치는 저자 보고값이며 우리 팀이 새로 측정한 결과가 아닙니다. 파일 크기와 실행 중 메모리, 소비 전력과 추론당 에너지도 구분합니다.
