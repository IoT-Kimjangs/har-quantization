# PAMAP2 재현·양자화·Mac 성능 비교

## 먼저 읽을 결론

PAMAP2도 모델·데이터 준비 → 원본 평가 → TFLite FP32 → 양자화 → Mac 속도·메모리 비교까지 완료했습니다.

**현재 공개 모델과 공개 코드 기준 정확도는 97.368421%, Macro-F1은 96.736122%입니다.** 논문 11쪽 표 3의 98.480%·97.978%에는 미치지 못했습니다. 원본 코드의 전처리 함수를 직접 분리해 대조했고, 현재 준비한 정제 행·구간·학습/평가 배열이 정확히 일치했습니다. 결과를 논문 수치의 완전한 재현으로 표기하지 않습니다.

속도는 이번 Mac 측정에서 동적 INT8이 가장 빨랐습니다. 연산 스레드 1 설정에서 TFLite FP32보다 중앙 지연시간이 약 **53.63% 감소**했습니다.

## 1. 데이터와 모델 준비

- 데이터: [UCI PAMAP2 공식 배포](https://archive.ics.uci.edu/dataset/231/pamap2+physical+activity+monitoring), DOI `10.24432/C5NW2H`. UCI 페이지에는 CC BY 4.0으로 표시됩니다.
- 사용 파일: Optional 5개 + Protocol 9개, 총 14개 `.dat`. 원본·설명 PDF·ZIP은 `data/raw/pamap2/`에 보관하고 Git에서 제외했습니다.
- 원본 전체 행: **3,850,505개**, 공식 데이터 설명과 일치합니다.
- 저자 코드: [고정 커밋](https://github.com/AASIFRASHIDKHANDAY/PATCH-BASED-TRANSFORMER-WITH-QUANTIZATION/tree/90eb53deec3ff166fa0f1e08211d8d9d1770411d)의 `code/Baseline Transformer/PAMAP2TRANSFORMER_BASELINE.ipynb`.
- 저장 모델: `pamap2_transformer_best_fp32.keras`, 3,155,086바이트, 저장 Keras 3.13.2. 로컬 `models/`에만 보관합니다.
- 모델 SHA-256: `bf623195e5b288bbf42c3e83cb4da7d9291401264b7c682cd5a775bfedfd943d`.
- 실제 모델 로드: `(None, 200, 19)` → `(None, 18)`, 별도 커스텀 레이어 없이 안전 모드로 로드 성공.

## 2. 공개 코드 기준 전처리

재귀적으로 찾은 `.dat` 경로를 정렬하므로 Optional 다음 Protocol 순서입니다. 원본 코드처럼 선택한 19채널과 행동만 유지하고 활동 0·결측/무한대 행을 제외한 뒤 이어 붙입니다. 사용자·타임스탬프별로 다시 정렬하거나 사용자 경계에서 구간을 끊는 처리는 추가하지 않았습니다.

| 항목 | 행/구간 수 |
| --- | ---: |
| 원본 행 | 3,850,505 |
| 활동 0 제외 | 1,125,552 |
| 이후 선택 열의 결측·비유한 행 제외 | 2,478,241 |
| 남은 유효 행 | 246,712 |
| 길이 200·이동 100의 전체 구간 | 2,466 |
| 학습 구간 | 1,972 |
| 평가 구간 | 494 |
| 파일 경계를 가로지르는 구간 | 26 |

행동 라벨은 구간의 최빈값입니다. 구간 단위 80:20 층화 분할, seed 42를 적용하고 학습 구간의 모든 시점으로 StandardScaler를 맞춘 뒤 평가에 적용했습니다. 원본 실행 때의 scaler·분할 인덱스는 공개되지 않아 같은 절차로 재계산한 통계를 사용합니다.

원본 IMU의 명목 샘플링은 100Hz지만, 결측 행을 제거한 뒤의 연속 200개 유효 행이 항상 원본 시간 2초를 뜻하는 것은 아닙니다. 현재 코드는 원본과 같이 시간 간격·사용자 경계에 따라 구간을 추가 분리하지 않습니다.

[전처리 실행 기록](../results/pamap2-preparation/summary.json)과 [원본 함수 대조 기록](../results/pamap2-preparation/reference-check.json)을 남겼습니다. 대조에서는 해시가 고정된 원본 노트북에서 로딩·구간 함수 두 개만 분리해 실행했습니다. 노트북 전체나 모델 학습 코드는 실행하지 않았습니다. 14개 파일의 정제 행, 전체 구간, 표준화한 학습·평가 배열과 정답이 모두 정확히 일치했습니다.

## 3. 정확도와 양자화

494개 평가 구간 전부를 동일한 순서로 실행했습니다. Keras는 배치 128의 `model(x, training=False)`, LiteRT는 배치 1·CPU 스레드 1로 평가했습니다.

| 모델 | 파일 크기(KiB) | 정확도 | Macro-F1 | 정답 수 |
| --- | ---: | ---: | ---: | ---: |
| Keras | 3,081.138672 | 97.368421% | 96.736122% | 481 |
| TFLite FP32 | 996.960938 | 97.368421% | 96.736122% | 481 |
| FP16 | 523.468750 | 97.368421% | 96.736122% | 481 |
| 동적 INT8 | 315.875000 | 97.368421% | 96.736122% | 481 |
| INT8 입출력·일부 FP32 | 326.679688 | 97.570850% | 96.867314% | 482 |

Keras·FP32·FP16·동적 INT8은 행동 예측이 모두 같습니다. INT8 입출력 모델은 1개 구간에서 다른 행동을 예측해 정답이 1개 늘었습니다. 작은 평가셋의 1개 차이를 일반적인 성능 향상으로 주장하지 않습니다.

전체 정수 INT8 설정에는 학습 구간 300개를 seed 42로 중복 없이 선택해 사용했고 평가 구간 번호 중복은 0개였습니다. 기존 중첩 구간 분할 때문에 원본 시점까지 분리됐다는 뜻은 아닙니다. 선택 번호와 해시를 기록했습니다.

INT8 입출력 모델에는 **float32 텐서 12개, NEG 연산 6개**가 남아 `integer_only_achieved=false`로 기록했습니다. 파일·variant 이름의 `int8_full`은 요청한 설정 식별자이며 실제 산출물을 완전 정수 모델로 부르지 않습니다. SELECT_TF_OPS나 모델 구조 변경은 하지 않았습니다. 평가 입력에서 int8 범위를 벗어나 clipping한 값은 2개였습니다.

FP32 최대 출력 확률 차이는 Keras 대비 약 `5.96e-7`입니다. 전체 모델의 혼동행렬·출력 진단·파일 해시는 [모델 평가 JSON](../results/2026-11-10-macos-pamap2-models/metrics.json), 구간별 결과는 같은 폴더의 [예측 CSV](../results/2026-11-10-macos-pamap2-models/predictions.csv)에 있습니다.

### 논문 보고값과의 차이

논문 11쪽 표 3은 정확도 **98.480%**, Macro-F1 **97.978%**입니다. 현재 Keras 결과는 각각 **-1.111579%p**, **-1.241878%p** 낮습니다.

494개 평가 구간에서는 정답이 1개 바뀔 때 정확도가 약 0.202429%p 변합니다. 이 평가 수에서 논문의 98.480%는 정수 정답 개수로 나올 수 없는 표시값입니다. 현재 공개 코드가 만드는 평가셋과 논문 수치가 연결되는 원본 분할·전처리 기록을 더 확인해야 합니다. 원인을 특정 전처리나 하드웨어 탓으로 단정하지 않고 차이 자체를 기록합니다.

## 4. Mac 속도·프로세스 메모리

조건마다 독립 프로세스에서 배치 1·워밍업 50회·측정 1,000회를 실행했습니다. 평가 구간이 494개이므로 seed 42로 순서를 섞은 뒤 **같은 494개를 순환해 1,000회** 측정했습니다. 서로 다른 평가 구간 1,000개를 사용한 것이 아닙니다. 12조건 모두 같은 입력 순서를 사용했습니다.

### 연산 스레드 1 설정

| 실행 방식 | 중앙값(ms) | p95(ms) | 프로세스 피크 RSS(MiB) |
| --- | ---: | ---: | ---: |
| Keras predict() | 25.687333 | 27.703402 | 510.70 |
| Keras 직접 호출 | 19.629521 | 20.748927 | 484.78 |
| TFLite FP32 | 0.255375 | 0.274717 | 68.48 |
| FP16 | 0.255916 | 0.273519 | 68.31 |
| 동적 INT8 | **0.118417** | 0.134218 | 67.34 |
| INT8 입출력·일부 FP32 | 0.262875 | 0.293120 | 67.30 |

### 런타임 기본 설정

| 실행 방식 | 중앙값(ms) | p95(ms) | 프로세스 피크 RSS(MiB) |
| --- | ---: | ---: | ---: |
| Keras predict() | 25.970730 | 30.846942 | 511.72 |
| Keras 직접 호출 | 19.391375 | 20.397198 | 485.94 |
| TFLite FP32 | 0.255625 | 0.272274 | 68.52 |
| FP16 | 0.256042 | 0.289460 | 68.03 |
| 동적 INT8 | **0.119292** | 0.128047 | 67.17 |
| INT8 입출력·일부 FP32 | 0.262917 | 0.288602 | 68.08 |

동적 INT8은 FP32 대비 중앙 지연시간이 1스레드 설정에서 약 53.63%, 기본 설정에서 약 53.33% 짧았습니다. FP16은 크기가 줄었지만 지연시간은 FP32와 비슷했고, INT8 입출력 모델은 소폭 더 긴 시간이 관측됐습니다. 작은 시간·메모리 차이에 통계적인 우열 의미를 부여하지 않습니다.

지연시간은 호출과 출력 준비까지 측정하며 INT8 입력 양자화·출력 역양자화를 포함합니다. 모델 로드·초기화·파일 I/O는 제외합니다. Keras 직접 호출의 `.numpy()` 완료까지, LiteRT는 set_tensor·invoke·get_tensor까지 측정합니다. RSS는 런타임·입력·모델을 포함한 전체 프로세스 피크이며 모델 가중치만의 RAM이 아닙니다. LiteRT 프로세스는 TensorFlow를 import하지 않았습니다.

1스레드는 연산 설정이며 전체 OS 스레드 하나를 뜻하지 않습니다. 실제 관측 스레드와 전원·패키지 상태는 [환경 및 원시 기록 폴더](../results/2026-11-10-macos-pamap2-benchmark/summary.json)에 남겼습니다. 배경 앱·CPU 주파수·열 상태는 통제하지 않았으며 한 Mac 세션의 결과입니다. 다른 기기나 Windows에서도 같은 절대 속도를 기대하지 않습니다.

12조건 × 1,000회 원시 CSV에서 입력 순서·행 수·파일 해시·중앙값·p95를 독립 검증했고, 12,000개 행동 예측이 이전 전체 평가 기록과 일치했습니다.

## 재실행 순서

같은 프로젝트의 Mac 가상환경과 [설정](../configs/pamap2.json)을 사용합니다. 원본 데이터와 모델·처리 배열은 Git에서 제외됩니다. 기존 결과는 덮어쓰지 않으므로 재실행 시 먼저 기존 파일을 확인합니다.

```bash
# 공식 UCI ZIP 다운로드 후 실행
.venv/bin/python scripts/prepare_pamap2.py --archive '/path/to/pamap2+physical+activity+monitoring.zip'
# 해시가 고정된 저자 노트북과 전처리 결과 대조
.venv/bin/python scripts/check_pamap2_reference.py --notebook '/path/to/author/code/Baseline Transformer/PAMAP2TRANSFORMER_BASELINE.ipynb'
# 모델 전체 평가·변환·양자화
.venv/bin/python scripts/evaluate_pamap2_models.py --output results/2026-11-10-macos-pamap2-models
# Mac 속도·메모리
.venv/bin/python scripts/benchmark_pamap2_macos.py --output results/2026-11-10-macos-pamap2-benchmark
```

저자 저장소를 고정 커밋으로 체크아웃하고 `models/pamap2_transformer_best_fp32.keras`를 로컬 `models/`에 준비합니다. 준비 스크립트가 모델·ZIP 해시를 확인하고 공식 ZIP 내부 파일도 CRC 검사 후 풉니다. ZIP이 바뀌었다면 해시를 자동 갱신하지 않고 멈춥니다.
